# GATE10_TOP_LEVEL_FAILURE_ANALYSIS

**Analysis date:** 2026-07-06 (of 20260706-0213 evidence run)  
**Branch:** a-plus-maturity/20260705-1649  
**Context:** Gate 10 RISC0 real-receipt closure (A+ maturity plan)

## Summary of Finding
The top-level evidence bundle verdict was FAIL (manifest "verdict": "FAIL") even though the RISC0 cryptographic path was fully real and passing. The root cause was a non-RISC0 check: the solver obligation generated by the fixture's `assert`.

## Exact Failing Check
- Check name: `solver`
- Status: `FAIL`
- Detail: `assert:(= y (_ bv42 32))=FAIL`

This single failing check caused the overall bundle verdict to be FAIL via status propagation in the evidence manifest.

## Exact File Causing Failure
- `implementer/a_plus_audit_run/20260706-0213/gate10_risc0_with_real_receipt/proof_bundle/evidence-20260706-021338-safe/source.anubis`

Contents (the fixture used for that run):
```anb
fn main() {
    let x: u32 = 7;
    let y: u32 = x * 6;
    assert(y == 42);
}
```

Supporting files:
- `.../evidence.json` (the checks array)
- `.../manifest.json` (top-level verdict)
- `.../analysis/solver.smt2` and `solver_replay.json` (the SMT encoding of the negation of the assert)

## Whether the Failure Is Real or Stale
**Real.** 

The solver was correctly reporting that the asserted property does not hold for all possible inputs. With a free variable `x`, the program admits values of `x` that make `y != 42`. The SMT solver found a model for the negation of the assert. This is expected behavior for the current solver integration when an `assert` is present over derived values from unbound inputs.

No staleness: the receipt, ImageID, ELF, and risc0_metadata were freshly generated in that run.

## Root Cause Category
- **Primary: fixture semantics** — the chosen source contained an `assert` on a value derived from a free input variable. The current Anubis solver treats top-level asserts as universal obligations in this context.
- **Secondary: bundle status propagation** — a FAIL in any listed check (including solver) results in overall bundle verdict FAIL (see manifest.json).
- **Not the cause:**
  - Schema or command status bugs
  - RISC0-specific analysis / verifier logic (risc0_receipt_verify and all hybrid_* sidecar hash checks were PASS)
  - Dev/mock/cache (metadata explicitly false)
  - Placeholder ID (real ImageID from risc0-build)

RISC0 crypto successes in the same bundle (for contrast):
- `risc0_metadata.json`: `verify_status: "passed"`, `fresh_receipt_generated: true`, `cache_used: false`, `dev_mode: false`, `mock_prover: false`, `image_id_is_placeholder: false`
- Real `receipt.bin` (~209 KB), real `guest.elf`, real ImageID extracted via risc0-build
- `receipt.verify.log` + standalone `verify-receipt` both PASS
- All `hybrid_*` checks in evidence.json: PASS
