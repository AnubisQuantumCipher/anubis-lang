## Boundaries and follow-up

1. **The origin is an in-process row ordinal, not a stable obligation identity.** A malformed producer that associates the wrong SMT or status with the current obligation can still issue the expected ordinal and name. In particular, equal-name obligations may exchange result contents while keeping positional origins, and the validator does not compare `smt`, assumptions, assertion, model, or proof detail to the obligation (`captured.rs:403-421`). The duplicate-name synthetic control catches a copied or reordered *issued row with its origin* (`captured.rs:1308-1339`); it does not establish formula-to-source correspondence. This is consistent with the patch's bounded description and is not a blocker to the internal row-integrity increment.
2. **An obligation omitted before `TypedIR.solver_obligations` is invisible here.** The producer and validator share that same final vector (`captured.rs:480-484`). This patch cannot close missing expression-position, stale-fact, or omitted-call obligations. The normal CLI and evidence consumers continue through `check_obligations` and do not receive source ordinals. Public assurance therefore remains HOLD until a source obligation inventory and independent correspondence check exist.
3. **The test hook deliberately admits synthetic `PASS` rows with arbitrary detail and SMT** when ordinal/name/count match (`captured.rs:1257-1277`). This is acceptable for an inventory-shape unit test, but its positive result must never be described as proof authentication. The real `g(5)`/`g(0)` twin is the relevant integration control, subject to the lead's retained logs and exact candidate identity.
4. `SolverStreamIntegrityError` is exposed through the public `middle` module (`compiler/src/lib.rs:13`, `middle/mod.rs:204-213`). The final local diff adds `#[non_exhaustive]` to this enum (`middle/mod.rs:204`). I reviewed that exact change on `middle/mod.rs` SHA-256 `6abfc5e3359adb535a42a64a84de78b746d5df93ffea81ca4a9aa9ed0f4a981c`; `captured.rs` remains `c2b1cd45899a96b05f221b645e8d1eb1769ce1955bcc13c588856f6756dc8a5c`. The attribute creates an explicit future evolution contract for downstream Rust matchers and does not alter in-crate matching, solver classification, or serialized checks. It does **not** preserve source compatibility for any pre-existing external code that already matched this previously exhaustive public enum: both the new variants and the attribute require such code to add a wildcard arm. I found no such downstream use in the repository search. Because this is an unpublished branch API, this does not block the bounded integration, but a stable Rust API claim would need a downstream compatibility decision.
