## Semantic checks and limits

`compiler/src/backends/run.rs:5125-5187` lowers a lambda by identifying free local values and callees, cloning them at definition, and moving those snapshots into the closure. That supports the intended early-`g` capture semantics. The saved Safe checks establish analyzer outcomes; no native execution was run to test compiler/runtime agreement. The concrete `main` calls `emit(42)` only, so it is not itself a two-input differential runtime witness. The information-flow claim is about the secret formal `s` over possible inputs and the presence of a public output event. The capture invalid diagnostic names `<closure>`, which does not identify the exact closure or call site in structured output.

`compiler/src/middle/ifc2/eval.rs:644-663` checks public egress under a secret PC and emits the observed `[ifc2]` message. The direct `reject_implicit_flow_under_secret_pc` implementation at `compiler/src/middle/mod.rs:27703-27729` concerns assigned public roots; its diagnostic wording is different. Therefore the matching code `ANUBIS_IMPLICIT_FLOW` alone cannot identify the producer. Registration should preserve the observed producer in the baseline receipt and use a separate direct-producer oracle when the new transfer is implemented. The current JSON lacks a structured producer/source span for these findings, so a direct producer closure claim cannot be inferred from the typed code alone.

The early-return pair tests a definite return versus a known-true assertion that continues. It does not cover an assertion that can fail, a may-abort function, exception propagation, or termination-channel behavior. Its old `v7-next-controls/` invalid source returned public `i64` and the saved earlier output contained an additional public-return refusal. Keep that earlier observation as history; the revised `secret<i64>` source is a distinct immutable case identity, not a silent replacement. The current `D9_V7_NEXT_PRODUCTION_TRANSFER_DESIGN.md` table still lists the old early-return SHA values and `UNRUN` rows; its later note documents the revision. Update the table with the exact revised identity and scoped observed outcomes in a separate documentation commit after fixture registration, retaining the old observation.
