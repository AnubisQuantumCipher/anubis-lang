## Findings

No newly introduced false accept or diagnostic laundering was found in the changed, closed grammar. This is a static judgment with the validation limits below.

- The direct PC producer still collects original assigned roots before filtering (`compiler/src/middle/mod.rs:16211-16229`). The new classifier runs only for a Safe secret PC; `pc_closed_writes` refuses unsupported condition or arm syntax (`:27783-27793`). `pc_closed_read` is an explicit, pure subset: variable/literal reads, Boolean negation, comparison, and Boolean conjunction/disjunction (`:27734-27752`). Calls, blocks, match/if expressions, field/index access, casts, and other expression forms are not certified. The current native comparator is an internal value operation, not a user function call (`compiler/src/backends/run.rs:1953-1970,4660-4688`).
- The binding site is the arm and statement index (`compiler/src/middle/mod.rs:27705-27724`). Each arm starts with a fresh local table; a `let` affects only subsequent assignments in that arm (`:27754-27781`). Thus an outer write before a shadow, a public re-shadow, and a write in the other arm remain unprotected. The classifier removes a name only when every classified write resolves to a protected branch-local declaration and its root set equals the original independent collector's set (`:27796-27821`). A root-scan mismatch preserves the old refusal.
- Native lowering gives each statement-`if` arm a lexical Rust block, lowers `let` as a new binding, and lowers a plain assignment as a rebinding (`compiler/src/backends/run.rs:3590-3622,3689-3708`). This supports the oracle interpretation: the public outer `out`/`public_value` is unchanged by the protected shadow. The enforcing analysis snapshots and restores block scope and keeps separate branch states (`compiler/src/middle/mod.rs:16258-16322`).
- Filtering changes only the local `assigned` set passed to `reject_implicit_flow_under_secret_pc`; solver/frame invalidation later still uses `collect_assigned_roots` independently (`compiler/src/middle/mod.rs:16361,16377-16386`). I found no new stale-fact path from this patch. It does not alter `expr_is_secret_pc`, other IFC lanes, the runtime, or evidence-status code.
- A positive could be accepted for the wrong reason if a later checker stopped seeing the secret guard or the native backend bound a different variable. The applied source keeps the original `expr_is_secret_pc` check (`compiler/src/middle/mod.rs:16220,28025-28040`), and the native block/binding lowering cited above supports the intended lexical semantics. Still, only lead-owned candidate checks and runtime/source-bound evidence can establish the actual verdict and executed behavior. In particular, an invalid case rejected only by IFC2 exfiltration is insufficient for the **direct** `ANUBIS_IMPLICIT_FLOW` oracle.
