## Blocking findings

1. **A present but failed optional z3 cross-check is treated as absence, and the captured result can still be `Proved`.** The new `z3_spawn_first_line()` uses `z3_spawn_first_line_observed(smt).ok()?.0` (patch lines 815–864; projected `middle/mod.rs:21916`). This collapses `Spawn`, `Wait`, empty stdout and warnings-only stdout to `None`; it also discards the helper's `write_failed` flag. In the native-authoritative primary UNSAT branch (patch around projected `middle/mod.rs:21356–21427`), `None` falls through to `IssuedSolverOutcome::Proved`. In the native SAT branch it produces `Disproved`; in native vacuity (projected `middle/mod.rs:21236–21275`) it returns native `Satisfiable` or `Contradictory`. The product default enables native authority (`middle/mod.rs:21651–21661` in the base); `PreparedCapturedProject::check_and_lower_safe_rust()` reaches this producer at `captured.rs:483`. An independently checked native result may be sufficient when z3 is genuinely absent, but a spawned process with no answer, failed write/read, or abnormal termination is a different event. The patch's typed tool-failure promise does not hold for that common captured path. Distinguish a deliberately optional absent z3 from a present broken process, propagate the latter as a typed failure, and retain the native-only policy explicitly.

2. **The native vacuity cross-check ignores a malformed non-error answer.** In `assumptions_satisfiable` (patch around projected `middle/mod.rs:21236–21275`), a first line such as `maybe` passes `z3_rejected_query`, yields no `zb`, and the function returns native `Satisfiable`/`Contradictory`. With native `Satisfiable`, a previously proved contract stays `IssuedSolverOutcome::Proved` in `check_obligations_with` (projected `middle/mod.rs:21025–21054`). The new pure `vacuity_answer(Some("maybe"))` would correctly return a typed `MalformedResponse`, but this native-first branch never calls it. This is the same missing producer transfer in an additional, independently reachable branch. Cover valid matching response, literal `unknown`, declared resource refusal, explicit rejection, malformed response, and absence at the actual native-first seam.

3. **A nonzero z3 process exit can still become `Proved` in the z3-only fallback.** `run_z3_obligation_with_smt` waits successfully but never inspects `output.status` before passing stdout to `classify_obligation_z3_answer` (patch around projected `middle/mod.rs:21528–21616`). That classifier maps `unsat` to `IssuedSolverOutcome::Proved` even when the process exited abnormally. The query deliberately includes a later `(get-model)`, so a blanket rule that every nonzero exit invalidates an earlier `unsat` needs careful compatibility review; nevertheless, the current producer has no distinction at all. A test substitute that writes `unsat` and exits nonzero would expose the boundary. Define which completed solver transcript is authoritative, distinguish expected later-command errors from process failure, and give the latter a typed outcome. The worker manifest explicitly names process exit as unclassified, so this is a limit of this patch, not a claim that it newly introduced the path.

## Other review points

- The primary z3 `stdin.write_all` error branch returns `ToolFailure::Write` immediately (projected `middle/mod.rs:21501–21517`) without visibly closing/reaping that owned child. That was true of the previous refusal path too, but the new typed process-failure lane should own child cleanup. This is a plausible leftover-process source, not a reproduced leak; no process was run here.
- In the vacuity fallback, `z3_spawn_first_line_result` first reads the answer and then returns `Write` whenever `write_failed` is set (patch lines 827–833). If the process emitted `(error …)` before closing stdin, the typed reason becomes `Write` and the display says "returned no answer", although a rejection answer was observed. Both refuse, but the failure stage is wrong. Preserve the observed response and prioritize an explicit query rejection over an ambiguous partial-write error.
- The inventory consistency check tests only whether typed outcome and wire status agree about `PASS` (projected `captured.rs:446–457`). Thus fabricated `Disproved` + wire `UNKNOWN` or `Undecided` + wire `FAIL` passes the check. The latter pairing is currently used for native-proof-policy refusal, so a rigid one-to-one map is not appropriate. At minimum, specify the allowed status set per typed outcome and test each producer combination. The current predicate is sufficient to reject `ToolFailure` + `PASS`, but does not fully enforce its `OutcomeStatusMismatch` name.
- The patch retains `SolverCheck` serialization and its public caller: `SymbolicEngine::check_obligations` projects `ProducedSolverCheck.check` (projected `middle/mod.rs:20903–20911`). `CapturedSafeCheckFailure` is crate-private. No external public API expansion was seen in this diff. The private captured bridge still returns only raw `SolverCheck` rows for `Disproved`, `ContradictoryPremises`, `Undecided`, and `Unencoded`; typed distinctions beyond tool failure do not yet reach a consumer or persisted evidence.

## Good transfer and required validation

The patch attaches producer outcomes at the obligation branches, changes vacuity after a typed `Proved`, and demotes only a typed checked `Disproved` under over-approximation. It no longer uses display prose to select the captured tool-error lane. Its in-memory inventory ordering/name guard remains intact. These are useful changes, but the native-first exceptions above prevent a complete typed failure claim.

The added tests cover pure response classifiers, over-approximation, forged detail text, mixed rows and a positive Safe call. They do not execute a controlled subprocess through the native-first cross-check or the main process-exit/partial-write path. After fixing the producer, the lead should run source-bound focused tests with an isolated solver executable seam, plus a real z3 positive control and a same-corpus public `SolverCheck` comparison. This report is static review only; it establishes neither runtime reproduction nor a full semantic soundness verdict. It does not assert source-to-obligation completeness, a public CLI outcome, an evidence seal, or native lowering correspondence.
